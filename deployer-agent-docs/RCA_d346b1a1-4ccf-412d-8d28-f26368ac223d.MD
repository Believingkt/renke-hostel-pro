# RCA — renkeduo initial deploy: build_image failure (FIXED, now LIVE)

## Outcome
Recovered. App is live at https://renkeduo.emergent.host (`/api/health` → 200 `{"status":"ok"}`).
Winning run: `d346b1a1-4ccf-412d-8d28-f26368ac223d`.

## Symptom
`build_image` failed on runs `e6bb3c63...` and `9cc26818...` (deterministic). The error surfaced only as
`wait $BUILD_PID … exit status 1` + `ERROR: …/customers-app:<tag>: not found` (image never pushed to ECR).
BuildKit's real stderr was NOT in the retrievable CodeBuild log — the parallel `build-frontend-artifacts.sh`
output (thousands of `cp … s3://` lines) flooded the readable 500-line window, hiding the actual buildx error.

## Root cause (reproduced in sandbox)
The app is a **yarn-workspaces monorepo** (`vite_react_shadcn_ts`, real app at `apps/booking` = `@lakeze/booking`).
`frontend/` is only a shell package whose `build` script is:
`cd .. && yarn install --frozen-lockfile --ignore-engines && yarn build:booking && cp -r apps/booking/dist frontend/build`.

The cloud build always builds `Dockerfile.cloudbuild` with `--target final-build`, whose `frontend-build` stage does
`COPY frontend/ /app/` then `yarn build`. Because only `frontend/` is copied (not `apps/`, `packages/`, root
`package.json`/`yarn.lock`), the script's `cd ..` lands in a dir with no workspace root. Reproduced exactly in the eph pod:

```
$ cd .. && yarn install --frozen-lockfile --ignore-engines && yarn build:booking && ...
error Couldn't find a package.json file in "/..."
error Command failed with exit code 1.   (YARN_EXIT=1)
```

The separate Cloudflare `build-frontend-artifacts.sh` step SUCCEEDS because it runs from `${SOURCE_DIR}/frontend`
with the full repo present (`cd ..` reaches the real monorepo root) and publishes the fresh frontend to R2.

Ruled out (verified clean): backend `requirements.txt` installs fully (real `pip install --no-deps` with the emergent
extra-index, Python 3.11.14, EXIT=0 — no missing/hallucinated package); `server.py` valid; `pip-cache/{pip-wheels,pip-bin}` present.

## Fix applied (manifest only)
Wrote the full manifest set to GCS; changed ONLY the `frontend-build` stage of `Dockerfile.cloudbuild`.
Since this is a **Cloudflare** frontend, the user-facing frontend is built by `build-frontend-artifacts.sh` and served
from R2; the `final-build` image stage only supplies the pod's nginx fallback static files (health_check skips `GET /`
for CF frontends). The stage now reuses the prebuilt `frontend/build` (valid `index.html`) already shipped in the
source instead of running an in-image monorepo `yarn build` that cannot work from `COPY frontend/` alone:

```
RUN mkdir -p /frontend-output && \
    if [ -d "build" ]; then cp -r build/. /frontend-output/; \
    elif [ -d "dist" ]; then cp -r dist/. /frontend-output/; \
    else echo "ERROR: No prebuilt build or dist directory found"; exit 1; fi
```

All other manifest files were written back verbatim. Backend pip install path unchanged.

## Note for E1 (optional, not blocking)
The pod's embedded (nginx-served) frontend is now the committed `frontend/build`, which may lag the fresh R2 build —
harmless for this Cloudflare deployment because users are served from R2. If you prefer the image to always bake a
fresh frontend, make the `frontend-build` stage `COPY . /app/` and build from `/app/frontend` (mirrors the working
`build-frontend-artifacts.sh`); note that is heavier (frontend built twice).
