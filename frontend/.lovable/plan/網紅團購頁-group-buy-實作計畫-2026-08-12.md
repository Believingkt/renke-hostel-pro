# 網紅團購頁（Group Buy）實作計畫

## 已定案的三件事
1. 訂金比例：**每個團購活動各自設定**（不吃館別 `booking_settings.deposit_percentage`）。
2. 匯款期限：**建單起算固定 72 小時**，逾期自動取消（不因入住日接近而縮短）。
3. 佣金：**團購訂單另立一套佣金**，不進現有 KOL／星探／團隊獎金試算。

---

## 先回答你的三個疑問

**實作後會影響、變更到任何現有功能嗎？**
不會改動現有功能行為。全部走「新增」而非「改寫」：新資料表、新前台路由、新後台分頁、新 Edge Function。唯一會被「共用讀取」的是既有庫存 RPC（`get_adjusted_room_inventory_batch`）與 `orders` 表 —— 讀取邏輯不動，只是多一個來源寫入訂單。既有 BookingFlow 的程式碼不修改。

**團購頁跟現有前台訂房頁會互相影響嗎？**
畫面與流程完全獨立（`/g/:slug`，自己的頁面元件）。但**庫存是共用同一份真實庫存**——這是你要的效果：團購賣掉會即時扣減一般訂房頁的可售數，反之亦然。互斥（包棟／散客）規則沿用現有 RPC，不另寫一套。價格則獨立：團購活動自帶方案價，不影響一般訂房頁售價。

**會跟營運分析、業主月結混在一起算嗎？**
會進入 `orders`，所以預設會被營運分析與業主月結看見（這通常是對的：真實入住、真實營收）。為了讓你能分流，做法是：
- 團購訂單一律標記 `order_source = 'group_buy'`，並在 `order_meta` 記 campaign_id。
- 營運分析的「訂單來源分析」自動多出「團購」這個來源，可獨立檢視。
- 業主月結：團購訂單**照常計入入住營收**（因為業主確實有收到住宿收入），但團購佣金屬平台端費用，**不寫入現有分潤欄位**，也不進 `team_commission_price` 的自動計算（在觸發器加 `order_source <> 'group_buy'` 的排除條件）。
- 若你希望業主月結也要排除團購，只要在活動設定加一個「計入業主月結」開關即可，這個開關我會一併做上去，預設「計入」。

## 資料庫（migration）

新增表：
- `group_buy_campaigns`：所屬館別、slug、標題、文案（富文本）、封面與圖片陣列、綁定的網紅（`kol_profiles`）、綁定折扣碼、販售期間、可入住日期範圍、狀態（草稿／上線／結束）、訂金百分比、匯款期限小時數（預設 72）、是否計入業主月結、佣金設定（見下）。
- `group_buy_campaign_packages`：活動對應可賣的方案／房型清單與團購價。
- `group_buy_bank_accounts`：每個活動的收款資訊（銀行名稱、代碼、戶名、帳號、備註）。可從館別預設帶入後覆寫。
- `group_buy_commissions`：團購專屬佣金紀錄（活動、網紅、訂單、營收基準、費率、金額、狀態：待結算／已結算），與現有 `commission_records` 完全分離。
- `group_buy_payment_events`：手動對帳軌跡（客人回報已匯款、後台確認收款、金額、對帳人、時間、備註），append-only。

存取規則（白話）：
- 團購頁內容、方案與價格：任何人可瀏覽已上線活動；只有該館管理者與總部可建立與編輯。
- 銀行帳號：只有下單成功的該筆訂單可讀取（透過訂單編號查詢的公開端點回傳），不開放整表匿名讀取。
- 佣金與對帳紀錄：僅館別管理者、總部可讀；網紅透過唯讀 token 頁只看到自己的彙總。
- 所有新表都會加上對應 GRANT 與 RLS。

`orders` 沿用既有欄位，不加破壞性欄位；團購專屬資訊寫進 `order_meta`（campaign_id、匯款截止時間、對帳狀態）。

## 後台（HQ／民宿後台）

新增側邊欄項目「團購活動」：
1. **活動列表**：狀態、期間、銷售筆數、GMV、實收訂金、逾期率。
2. **活動編輯**：基本資訊、文案與圖片、選擇可賣方案與團購價、綁定網紅與折扣碼、訂金比例、收款銀行資訊、佣金費率、是否計入業主月結。
3. **對帳工作台**：列出待確認訂單（客人已按「我已匯款」的排最前），顯示應收訂金／客人回報資訊，一鍵「確認收到訂金」→ 更新付款狀態、寫入對帳軌跡、自動寄出收款確認信、產生該筆團購佣金紀錄。
4. **團購分析**：以活動＋期間為維度的 PV、下單數、成交數、取消數、逾期未匯款率、GMV、實收訂金、平均客單、方案分佈、轉換漏斗；沿用現有「以入住日計／夜次均攤」切換與取消排除規則。
5. **網紅唯讀分享頁**：token 制公開連結（比照現有 KOL 公開頁），網紅只看到自己的成績與佣金。

## 前台流程

路由 `/g/:slug`（booking 網域）：
1. 團購頁：活動主視覺、文案、方案卡（團購價＋原價對比）、日期選擇。
2. 日期／方案選擇時即時查真實庫存（既有 RPC），售罄或不在可入住範圍即不可選。
3. 結帳：填旅客資料，自動套用綁定折扣碼（唯讀顯示，不可改），計算應付訂金（活動設定的比例）。
4. 送出後建立訂單（`order_source = 'group_buy'`，付款方式為銀行匯款），顯示匯款資訊與 72 小時倒數。
5. 訂單成立即寄出「訂房通知＋匯款資訊」信（含匯款截止時間與訂單查詢連結）。
6. 訂單查詢頁提供「我已完成匯款」按鈕（可填末五碼與匯款時間），按下後狀態轉為「待確認收款」並通知後台。
7. 後台確認收款後，客人收到「已收到訂金」確認信。

## 自動化

- 新 Edge Function `group-buy-expire-orders`，pg_cron 每小時執行：找出建單超過 72 小時且仍未收款的團購訂單 → 取消訂單、釋放庫存、寄出逾期通知信。已按「我已匯款」的訂單不自動取消，改標記為需人工處理。
- 收款確認時自動寫入 `group_buy_commissions`。

---

## 技術備註

- 庫存一律走 `get_adjusted_room_inventory_batch`，並沿用現有「下訂前後雙重驗證」流程（`src/lib/exclusiveAvailability.ts` 的判定），不另寫庫存邏輯。
- 價格計算沿用 `package_date_prices` 覆寫模式思維，但存在 `group_buy_campaign_packages`，避免污染一般售價。
- 信件走既有 Resend Edge Function 架構，新增三個樣板：訂房＋匯款資訊、已收到訂金、逾期取消。
- `team_commission_price` 觸發器加上 `order_source <> 'group_buy'` 排除條件，確保不進現有獎金體系。
