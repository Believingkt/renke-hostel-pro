# 2b：OTA 訂單修改信只改差異（設計摘要）

奧丁丁的 OTA 訂單收到修改信時，只調整真正有變動的部分，不再整批重建房間明細，所以已經排好的房號會保留。
訂單本身和房間明細改成同一個步驟一起寫入：其中任何一步失敗，整筆都不會改。

## 適用對象
- 民宿業主：OTA 訂單被修改後，已排好的房號和房價不會無故消失。
- 客服與營運：能清楚看到哪些修改信「已自動套用」、哪些「已擋下，需人工處理」、哪些是「舊信晚到，已略過」，告警會附上原因和信件裡的修改內容。

## 核心功能與行為
- **只改日期：** 房間明細原樣保留，在新日期重新檢查庫存和房號。
  - 原房號在新日期被別的訂單佔用時：訂單照改，那幾間房號清空，寄告警並列出哪幾間、被哪張訂單佔用。
  - 新日期庫存不足或備品不足時：整筆不改，寄告警。
- **同房型間數增加：** 原有的房間全部保留，只新增差額。新房間的房價取原有房間的平均，房號自動挑空房。
- **同房型間數減少：** 只刪差額。先刪還沒排房號的，再從房號排序最後一間開始刪。
- **整單換房型：** 舊房間全部釋放，依新房型重新建立並自動挑空房。
  - 信件金額有效時，房價 = 信件金額 ÷ 間數；否則沿用舊房間的平均房價。
- **只改人數或只改金額：** 只更新訂單，房間明細完全不動。
- **金額：**
  - 比對基準改為訂單原價（total_price）。
  - 信件金額大於 0 且不同時，才更新金額；已付款的訂單，已付金額同步改成信件金額。
  - 信件金額是 0 或空白時，不改任何金額。如果間數或房型有變，會另外寄告警，請人工核對總金額。
- **舊信晚到：** 以信件標頭的寄送時間判斷先後；比較舊的信不套用、不通知業主，只寄內部告警。
  - 任一邊沒有寄送時間時，改用信件抵達時間比較。
- **整筆擋下、不套用（fail-closed）：** 照常通知業主，並寄內部告警。擋下的情況如下：
  - 同一個 OBE 有超過一張未取消的訂單。
  - 現有明細有多個房型、某一列不是單間，或沒有任何明細。
  - 信件房型名稱在同館內對不上，或同時對上多個房型。比對分兩步：先比去空白、轉小寫後完全相同；沒有的話，再看信件名稱是不是剛好只是某一個房型名稱的開頭。不再使用「包含」比對。
  - 信件間數超過 20 間。
  - 信件解析不完整，而且要改的是日期、房型或間數。
  - 訂單已入住或已退房。
  - 訂單與明細的房型不一致。
  - 舊信判斷查詢失敗。
- **內部告警的內容：** 一律寫明「未套用，需人工處理」（擋下或舊信時）、原因代碼、OBE 編號、訂單編號，以及信件裡的修改內容（修改前 → 修改後）。

## 處理流程
1. 收到奧丁丁修改信，判斷擁有者。PMS 回音信的處理維持現狀，不在這次範圍。
2. 檢查這封是不是舊信晚到。是的話略過，記為「舊信已略過」，並寄內部告警。
3. 找出對應的訂單，比對信件和現有訂單、現有房間明細。
   - 屬於要擋下的情況時，記為「已擋下」，通知業主並寄內部告警。
   - 完全沒有差異時，記為「無差異」。
4. 訂單與房間明細在同一個步驟裡一起更新。
   - 成功時，記為「已更新」。有房號被清空、新房間沒排到房號，或金額需要人工核對時，另寄告警。
   - 失敗時，整筆不變，記為「套用失敗」，告警寫明原因：庫存不足、備品不足、重複送出保護，或訂單在比對後被別人改過。

## 介面與使用感受
- 業主端的畫面和通知信沒有任何改變。
- 營運端的信件處理紀錄，多出「舊信已略過」和「已擋下」兩種結果。告警信沿用現有的格式。房號衝突的列表格式跟補單頁的「未分配房號」一致。

## 實作階段
- **第一階段（這次施工的 MVP）：**
  - 單一交易的套用功能。
  - 只改差異的明細比對。
  - 先後順序判斷，並記錄信件寄送時間。
  - 擋下規則。
  - 告警與錯誤紀錄。
  - 測試。
- **第二階段（另外開批，需你決定）：**
  - 業主修改通知信的文字調整。
  - 告警信標題改成依情況顯示，現在一律寫「房型明細重建失敗」。
  - 重複的修改信會讓業主收到重複通知的問題。
- **第三階段（另外開批）：**
  - 後台與會員改期功能不會檢查房號衝突的既有漏洞。
  - 多房型修改信需要擴充信件解析。
  - 信件解析在「部分可比對」時，可能把修改前的值當成修改後的問題。

## 假設（未逐一詢問、由設計自行決定）
- 兩支既有函式的指紋改用 pg_get_functiondef 計算，與每日 RPC 合約檢查的算法一致，數值用使用者提供的正式庫實測值。
- 新函式除了只授權給 service_role，函式內也再檢查一次呼叫者必須是 service_role。
- 更新訂單時，會附上比對當下的入住日、退房日、房型、原價和狀態。這段期間如果訂單被別人改過，整筆不套用，記為套用失敗。
- 以下三種情況也一律擋下，屬於比你列的規格更保守的部分：
  - 訂單完全沒有房間明細（no_existing_rooms）。
  - 訂單上的房型與明細的房型不一致（order_room_type_mismatch）。
  - 信件解析狀態為空值（null）時，比照「解析不完整」處理。
- 間數增加時，新房間沿用現有第一列的專案（template）。
- 判斷舊信時查詢失敗，視為擋下，原因代碼是 stale_check_failed。
- 告警信沿用現有的 sendOrderRoomsAlertEmail，不修改它。所以信件標題仍是「房型明細重建失敗」，需要的說明寫在錯誤訊息欄位裡。
- 業主修改通知信（owlting-change-notify）本身不修改，只在 ingest 端讓「舊信晚到」不呼叫它。
